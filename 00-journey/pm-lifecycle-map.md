|---|---|

This table shows, for every document in this repository, **where a PM would normally write it** and **what actually happened here**.

| Phase | Document | Normally written | Here |
|---|---|---|---|
| Discovery | Problem statement and opportunity | Before build | Reconstructed after build |
| Discovery | Personas and jobs-to-be-done | Before build | Reconstructed; marked *Hypothesis* |
| Discovery | Competitor scan | Before build | Desk research, Nov 2026 |
| Definition | One-page brief | Before build | Reconstructed |
| Definition | PRD, user stories, acceptance criteria | Before build | Reconstructed from working behaviour |
| Definition | Scope and non-goals | Before build | Reconstructed |
| Definition | Success metrics | Before build | Proposed, not measured |
| Definition | Roadmap and prioritisation | Before and after launch | Proposed |
| Design | User journey, wireframes | Before and during build | Wireframes reconstructed from the UI |
| Design | Screenshots | After build | Captured Nov 2026 (blurred) |
| Architecture | System, data flow, sequences, ERD, algorithms, API spec | During build | Reconstructed from code |
| Delivery | RACI, decision log, dependencies, assumptions, risks | Throughout | Reconstructed |
| Quality | Test plan, UAT checklist | During build | Written after; no automated tests exist yet |
| Launch | Privacy and compliance, launch checklist, runbook | Before launch | Written before any launch |
| Reference | Glossary, open questions, changelog | Throughout | Written Nov 2026 |

## The principle

I would rather show an honest "reconstructed after build" tag than imply a perfect plan existed from day one. The value of the documents is that the next iteration starts from them.
